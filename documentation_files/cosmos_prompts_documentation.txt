Cosmos Reasoning Prompts — Design, Features, and Test Procedure


--- Purpose ---

Four Cosmos prompts were written, each designed to analyse the same
robotic screwing trajectory from a different angle. The idea was not
to have one monolithic "evaluate everything" prompt, but to split the
analysis into four specialised perspectives. Each prompt forces the
model to adopt a specific expert role and focus on a specific set of
features in the trajectory data. This way, the same raw joint-state
recording is examined four times, and each pass catches things the
others might miss.

All four prompts receive the same inputs: the task context (robot type,
screwdriver position, screw target, grasp parameters, joint limits) and
the recorded joint trajectory as a JSON array of timestamped snapshots.
The trajectory is sampled down to 80 waypoints to fit within the model's
context window.


--- The Four Cosmos Prompts ---


1. cosmos_screw.txt — General Screwing Evaluator

This is the broadest of the four prompts. The model is told it is an
expert evaluator for robotic screwing operations and is asked to do
a bit of everything: assess the reasoning quality, score the pick
phase, score the screwing phase, and check whether the reasoning
output matches the actual trajectory.

The prompt covers 13 scoring dimensions grouped into five categories:

  A. Reasoning Quality (4 criteria):
     - Spatial Awareness: whether the model identifies positions,
       orientations, and the geometric chain from grasp height through
       approach height to engage height correctly.
     - Phase Identification: whether the trajectory is segmented into
       the expected phases (home, open, approach, descend, close,
       retreat, move above screw, engage, CW rotation, lift, CCW
       reposition, re-engage, return home) with correct timestamp
       boundaries.
     - Screwing Mechanics Understanding: whether the model grasps that
       CW rotation only drives the screw when engaged, that CCW must
       happen while lifted, and that the wrist joint range forces the
       cyclic strategy.
     - Safety Awareness: joint limits, gripper stability during
       screwing, collision avoidance during transit, sequencing
       constraints.

  B. Trajectory Quality — Pick Phase (2 criteria):
     - Grasp Execution: approach angle, height, gripper value, retreat.
     - Pick-to-Screw Transition: smoothness, orientation maintenance.

  C. Trajectory Quality — Screwing Phase (4 criteria):
     - Screw Engagement: XY alignment, Z height, orientation.
     - CW Stroke Quality: joint isolation, step consistency, direction,
       limit compliance.
     - Lift-Reposition-Reengage Quality: correct sequencing every cycle.
     - Cycle Completion: all cycles finished, total rotation achieved.

  D. Trajectory Quality — General (2 criteria):
     - Smoothness: gradual transitions, no sudden jumps.
     - Efficiency: direct paths, appropriate speed per phase.

  E. Reasoning-Trajectory Alignment (1 criterion):
     - Consistency: does the trajectory match the reasoning output.

The prompt also defines six critical failure conditions that override
scores (gripper change during screwing, CCW at engage height, joint
limit violation, zero CW strokes, orientation deviation > 15°, missing
either pick or screw location). It includes a weighted scoring formula
where cycle completion is worth 20% and spatial awareness only 1%,
reflecting that actually finishing the screwing matters more than
correctly naming the workspace layout.

What makes cosmos_screw.txt distinct from the other three prompts is
that it also asks for recommended_waypoints — concrete replacement
joint configurations that the robot could use in a replanned execution.
This makes the output actionable rather than just diagnostic.


2. cosmos_fault_detection.txt — Fault Detection Specialist

This prompt casts the model as a fault-detection specialist. Its job
is to hunt for problems, not to give a balanced overview. The prompt
explicitly tells the model to complete its anomaly sweep before making
any overall quality judgement. The analytical focus is narrow and
specific:

  - Velocity anomalies: any joint velocity spiking beyond 2x the
    median velocity for that joint in a given phase. The model is
    asked to report timestamp, magnitude, and likely cause (overshoot,
    collision reaction, slippage).

  - Positional drift: comparing arm joints j1–j5 at the start vs.
    end of each screwing block. Drift beyond 0.02 rad is flagged as
    a sign that screw reaction torque or poor IK solutions are pulling
    the arm out of alignment.

  - Cycle-to-cycle consistency: whether CW stroke durations, wrist_3
    travel ranges, and lift/lower heights are consistent across the
    five cycles. Deviations beyond 15% from the mean are flagged.

  - Gripper integrity: any fluctuation in gripper state, even sub-0.01
    rad changes, as an indicator the screwdriver might be slipping.

  - Transition timing gaps: dead time between phases where no joint is
    moving. Gaps beyond 1.5 seconds are flagged as potential planning
    delays or controller hesitation.

  - Joint limit proximity: moments where wrist_3 comes within 0.2 rad
    of either safe limit. Repeated near-limit events suggest the cycle
    parameters need retuning.

  - Return-to-home residual: whether the final joint configuration
    matches home within 0.01 rad per joint.

The thresholds in this prompt (2x median velocity, 0.02 rad drift,
15% cycle deviation, 1.5s gap, 0.2 rad limit margin, 0.01 rad home
residual) were chosen to be tight enough to flag real issues without
triggering on normal motion planner noise. The screwing task has enough
structure and repetition that these thresholds are reasonable.

This prompt shares the same 13-dimension rubric and critical failure
conditions as cosmos_screw.txt. The difference is entirely in the
"Analytical Focus" section at the top, which steers the model toward
fault-oriented thinking rather than general assessment.


3. cosmos_energy_dynamics.txt — Dynamics and Energy Analyst

This prompt frames the analysis as a dynamics and energy-efficiency
problem. The model is told it is a robotics dynamics analyst whose
job is to reconstruct what the motors were doing at each phase, where
energy was wasted, and whether the velocity and acceleration profiles
are well-tuned for production.

The analytical focus areas are:

  - Velocity profile shaping: for each major phase (approach, grasp,
    transit, engage, CW stroke, lift, CCW reposition, return), the
    model is asked to characterise the velocity profile — is it
    trapezoidal (proper accel-cruise-decel), bang-bang (jerky), or
    does it have unnecessary reversals?

  - Acceleration demands: estimating peak acceleration at each joint
    from consecutive velocity changes. Anything beyond what a UR5e
    can reasonably produce (5–10 rad/s²) is flagged as suspicious.

  - Energy distribution across joints: during CW screwing, ideally
    only wrist_3 does work. If other joints show non-zero velocity,
    they are fighting reactive forces rather than contributing to the
    task — wasted energy.

  - Idle power consumption: periods where all joints are stationary
    but time is passing. The robot is holding against gravity with
    no productive output. The model is asked to quantify total idle
    time as a percentage of the full trace duration.

  - Phase transition efficiency: whether transitions between phases
    are crisp (< 0.5s near-zero velocity) or sluggish (> 1s dead
    time). Sluggish transitions indicate overly conservative planning.

  - Velocity scaling appropriateness: the robot should move slowly
    during engagement and CW screwing (precision) but faster during
    transit, lift, and CCW reposition (speed). The model checks
    whether the actual velocities reflect this priority.

  - Cumulative wrist_3 work: tracking total CW angular displacement
    vs. total CCW reposition travel. The ratio of productive CW
    to total wrist_3 travel is the "screwing efficiency ratio."
    Values below 50% mean the robot spends more wrist motion
    resetting than actually driving the screw.

This prompt is the only one that explicitly asks about energy-related
concerns. The others focus on geometric correctness, fault detection,
or process repeatability — none of them look at whether the velocity
profiles are well-shaped or whether the robot is wasting time at
standstill. The dynamics perspective fills that gap.

Like cosmos_fault_detection.txt, it shares the same 13-dimension
rubric and critical failure conditions as the base cosmos_screw.txt
prompt. The steering is done entirely through the analytical focus
section.


4. cosmos_process_quality.txt — Industrial Process Quality Engineer

This prompt adopts the perspective of a manufacturing quality inspector.
The question is not "did it work this one time?" but "would this
execution be acceptable across thousands of cycles on a real assembly
line?" The analytical focus is production-oriented:

  - Process capability (Cpk mindset): for each screwing cycle, the
    model measures key parameters — CW stroke range, stroke duration,
    lift height, CCW reposition range, re-engage position — and looks
    for cycle-to-cycle variation. A production-ready process should
    show less than 5% variation. Anything above 10% is flagged.

  - Takt time analysis: the total execution is broken into productive
    time (CW screwing while engaged) vs. non-productive time (transit,
    lift, CCW, settling, idle). A competitive screwing station should
    have productive time above 40% of total cycle time. Below 30%
    indicates the process needs redesign.

  - First-pass yield indicators: events that would cause a reject on
    a real production line — gripper slip, cross-threading (abnormal
    wrist_3 velocity suggesting resistance), incomplete engagement
    (rotation starting before the arm is fully lowered), missed
    cycles.

  - Positional repeatability: comparing arm joints j1–j5 at each
    engagement moment across all cycles. For production quality, the
    engagement position should repeat within ±0.005 rad. Beyond
    ±0.01 rad suggests the IK solver is not converging to consistent
    configurations.

  - Cycle time predictability: the total time per cycle should have
    a coefficient of variation below 8%. High variation means the
    planner is finding different paths each time.

  - Torque proxy analysis: without direct torque data, wrist_3
    velocity during CW strokes is used as a proxy. Constant velocity
    suggests free spinning (screw not engaged). Gradually decreasing
    velocity suggests increasing resistance (proper advancement).
    Sudden drops suggest jamming.

  - End-of-line readiness: does the robot leave the workspace in a
    clean state? Screwdriver properly handled? All joints returned
    to home? Any residual offset beyond 0.01 rad from home is treated
    as a line-stop condition.

This is the most production-focused of the four prompts. Where
cosmos_screw.txt asks "did it work?", cosmos_process_quality.txt
asks "would it survive a production audit?" The thresholds are
deliberately tighter than the fault detection prompt because
manufacturing tolerances are stricter than lab tolerances.


--- Why Four Separate Prompts Instead of One ---

A single monolithic prompt that covers all of the above would be
extremely long and would ask the model to switch cognitive roles
mid-response — from dynamics analyst to quality engineer to fault
detective. In practice, smaller models (like Cosmos 2B) handle
focused prompts better than kitchen-sink prompts. Each prompt is
between 150 and 200 lines, which is already pushing the limits of
what a 2B model can reliably follow.

Splitting the analysis also has a practical benefit for evaluation:
each Cosmos output is scored by a separate Llama evaluation, so the
scores can be compared across prompts. If the fault detection prompt
produces a low score but the general screwing prompt scores high,
that tells us the model handles broad analysis better than anomaly
hunting — which is useful diagnostic information about the model
itself.


--- Shared Structure Across All Four Prompts ---

Despite the different analytical perspectives, all four Cosmos
prompts share identical structure in several sections:

  - Task Context block: same placeholder fields for robot description,
    positions, grasp parameters, joint limits, cycle count, step size.

  - Inputs section: cosmos_reasoning_text and joint_trajectory_json
    placeholders, injected at runtime by the pipeline script.

  - Evaluation Rubric: the same 13 scoring dimensions (A through E),
    with identical score anchors (1/3/5 descriptions) for each
    criterion.

  - Critical Failure Conditions: the same 6 binary checks that
    override individual scores.

  - Scoring Weights: the same weighted formula for overall_score,
    with Cycle Completion at 20% and Spatial Awareness at 1%.

  - Output Format: the same JSON schema requiring per-dimension
    scores and justifications, plus recommended_waypoints.

The only thing that changes between prompts is the "Analytical Focus"
section at the top and the system role in the opening line. Everything
else is templated. This was a deliberate decision — by keeping the
rubric and output format identical, the four Cosmos outputs can be
compared on equal terms and the four Llama evaluations can be
aggregated into a single score table.


--- Test Procedure ---


Step 1 — Record a screwing trace

The continuous screwing task (test_screw_continuous.py) is executed in
MoveIt simulation. During execution, all joint states are recorded by
test_screw_continuous_cosmos.py, which subscribes to /joint_states and
writes every snapshot to a JSON file in outputs/screw_trace/. The
recording includes timestamps, all joint positions (arm + gripper),
and the total trace duration.


Step 2 — Run Cosmos on all four prompts

The script run_cosmos_4prompts.py loads the latest screw trace, samples
it down to 80 waypoints, and sends it to Cosmos through the same four
prompts. Each prompt is filled with the task context and trajectory
data, then sent to the Cosmos model via vLLM's OpenAI-compatible
endpoint (localhost:8000). The model generates a free-form text
response analysing the trajectory from its assigned perspective.

This step was run twice — once with nvidia/Cosmos-Reason2-2B and once
with nvidia/Cosmos-Reason2-8B. Both models received identical inputs.
The 2B model was the primary target; the 8B run was a comparison to
see whether the larger model produced better or different analysis.

Cosmos outputs are saved as both raw text (.txt) and metadata JSON
(.json, which includes the model name, elapsed time, and response
content) in outputs/cosmos/.


Step 3 — Evaluate with Llama

The script run_eval_4prompts.py takes each Cosmos output and feeds it
into the matching evaluation prompt along with the same trajectory
data. The evaluation prompts are sent to Llama 3 via Ollama
(localhost:11434) with temperature 0.1 and JSON output mode forced.

Llama acts as the judge. It reads the Cosmos analysis and the raw
trajectory side by side, then scores the Cosmos reasoning across the
13 dimensions. It also checks for critical failures, computes the
weighted overall score, and outputs improvement suggestions. The
evaluation results are saved as JSON in outputs/eval/.

The low temperature (0.1) was chosen to make the scoring as
deterministic as possible. The JSON output mode in Ollama forces
structured output so the scores can be parsed and compared
programmatically.


Step 4 — Compare results

The final step is manual. The four evaluation JSONs for a given model
run (2B or 8B) are read and compared across the four prompts. This
gives a matrix: 4 prompts × 13 dimensions × 2 models. The comparison
reveals which analytical perspective the model handles best, where it
struggles, and whether the 8B model actually outperforms the 2B on
domain-specific robotics analysis.
