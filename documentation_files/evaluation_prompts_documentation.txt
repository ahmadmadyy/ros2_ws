Evaluation Prompts — Design and Explanation


--- Purpose ---

The four evaluation prompts are the second stage of the pipeline. Each
one takes the text output from the corresponding Cosmos prompt, pairs
it with the raw joint trajectory, and hands both to Llama 3 for
scoring. Llama is the judge — it reads what Cosmos said and checks
it against what the robot actually did.

The reason a second model is used instead of having Cosmos score
itself is straightforward: self-evaluation is unreliable, especially
in small models. A 2B model that produced a wrong analysis is unlikely
to catch its own errors when asked to grade that same analysis. By
bringing in a separate model (Llama 3, running locally via Ollama),
the evaluation is independent from the reasoning. Llama has access
to the same trajectory data, so it can verify Cosmos's claims
against the ground truth.


--- The Four Evaluation Prompts ---


1. eval_screw.txt — General Screwing Evaluation

This is the evaluation counterpart to cosmos_screw.txt. It tells
Llama it is an expert evaluator for robotic screwing tasks and asks
it to score the Cosmos output across 13 dimensions.

The prompt is structured as a detailed rubric with explicit scoring
anchors. Each criterion has a table mapping scores 1, 3, and 5 to
concrete descriptions so that Llama does not have to invent its own
scale. For example, the CW Stroke Quality criterion defines:

  - Score 5: pure wrist rotation, consistent steps, correct direction,
    within safe limits.
  - Score 3: minor drift in other joints or slightly inconsistent steps.
  - Score 1: significant arm movement during screwing, wrong rotation
    direction, or joint limit violation.

The rubric is split into five sections:

  A. Reasoning Quality (4 criteria): Spatial Awareness, Phase
     Identification, Screwing Mechanics Understanding, Safety
     Awareness. These score how well Cosmos understood the task.

  B. Pick Phase (2 criteria): Grasp Execution, Pick-to-Screw
     Transition. These score the actual trajectory during the pick.

  C. Screwing Phase (4 criteria): Screw Engagement, CW Stroke Quality,
     Lift-Reposition-Reengage Quality, Cycle Completion. These are
     where most of the weight falls — the screwing is the point of
     the task.

  D. General (2 criteria): Smoothness, Efficiency. Trajectory-wide
     quality checks.

  E. Alignment (1 criterion): Consistency between what Cosmos described
     and what the trajectory shows.

The scoring weights are defined explicitly:

  Cycle Completion:              20%
  CW Stroke Quality:             15%
  Lift-Reposition-Reengage:      12%
  Screw Engagement:              10%
  Grasp Execution:               10%
  Consistency:                    8%
  Safety Awareness:               8%
  Screwing Mechanics:             5%
  Smoothness:                     4%
  Efficiency:                     3%
  Phase Identification:           2%
  Pick-to-Screw Transition:       2%
  Spatial Awareness:               1%

The weights were chosen to reflect task priority. Whether the screw
actually got driven (Cycle Completion, CW Stroke Quality) matters
far more than whether Cosmos correctly named the workspace layout
(Spatial Awareness). The heavy weighting on screwing-phase criteria
means a model that produces good spatial reasoning but misses the
actual screwing mechanics will still score poorly overall.

The prompt also defines six critical failure conditions. These are
binary — if any one triggers, it is flagged regardless of scores.
A model could score 5 on every dimension but still get a critical
failure flag if the gripper state changed during screwing.

Unlike cosmos_screw.txt, eval_screw.txt does not ask for
recommended_waypoints. The evaluation prompt's job is to score,
not to propose corrections. The output is a flat JSON of scores,
justifications, overall_score, and lists of critical failures and
suggestions.


2. eval_fault_detection.txt — Fault Detection Evaluation

This is the evaluation counterpart to cosmos_fault_detection.txt. The
opening paragraph is what sets it apart: it tells Llama that the
Cosmos reasoning it is about to evaluate was generated by a
"fault-detection specialist" whose primary focus was hunting for
velocity spikes, positional drift, gripper integrity issues, joint
limit proximity events, transition timing gaps, and return-to-home
residuals.

This framing matters because it tells Llama what to look for when
scoring. If Cosmos was supposed to be a fault detector but missed
an obvious velocity spike, Llama should score Phase Identification
or Safety Awareness lower — even if the broad structure of the
analysis was correct. The context line steers Llama's attention
toward whether Cosmos caught the faults, not just whether it
described the task in general terms.

The rest of the prompt — the rubric, scoring anchors, weights,
critical failure conditions, and output format — is identical to
eval_screw.txt. The only difference is that one sentence at the
top that tells Llama what kind of Cosmos output it is judging.

This design means the four eval prompts produce scores on the exact
same 13-dimension scale, making cross-prompt comparison possible.
If the fault detection Cosmos output scores 4.2 overall and the
general screwing Cosmos output scores 3.8, the difference is
attributable to the quality of the Cosmos reasoning under each
prompt, not to differences in the evaluation rubric.


3. eval_energy_dynamics.txt — Energy Dynamics Evaluation

The evaluation counterpart to cosmos_energy_dynamics.txt. The opening
tells Llama that the Cosmos reasoning it is scoring was generated by
a "dynamics and energy-efficiency analyst" whose focus was velocity
profile shaping, acceleration demands, energy distribution across
joints, idle power consumption, phase transition crispness, velocity
scaling appropriateness, and the ratio of productive CW wrist travel
to total wrist motion.

Again, the rubric, weights, critical failures, and output format are
identical to eval_screw.txt. The framing sentence is the only
difference. Llama is given context about what the Cosmos output was
supposed to be doing, so it can judge whether the dynamics analysis
was thorough and accurate — not just whether the output mentioned
the right positions and phases.

A practical consequence of this framing: if the Cosmos energy dynamics
output correctly identifies all phases and positions but says nothing
about velocity profiles or idle time, Llama should give lower marks
on criteria like Efficiency and Screwing Mechanics Understanding.
The eval prompt context ensures Llama knows that those omissions
are failures for this particular Cosmos output, even though they
would be acceptable in a general screwing evaluation.


4. eval_process_quality.txt — Process Quality Evaluation

The evaluation counterpart to cosmos_process_quality.txt. The opening
tells Llama that the Cosmos reasoning it is scoring was generated by
an "industrial process quality engineer" whose focus was process
capability (Cpk mindset), takt time breakdown, first-pass yield
indicators, positional repeatability, cycle time predictability,
torque proxy analysis from velocity profiles, and end-of-line state
cleanliness.

This is the strictest framing of the four. If the Cosmos process
quality output says the execution is "acceptable" but does not
discuss cycle-to-cycle variation or takt time, Llama should treat
that as a gap in the analysis — because a real process quality
engineer would not skip those checks. The eval prompt context
ensures Llama applies manufacturing-grade expectations to the
scoring.

The rubric remains identical. The output format remains identical.
The scores are directly comparable to the other three evaluations.


--- Design Decisions Across All Four Eval Prompts ---


Identical rubric, different framing

All four eval prompts use the same 13 dimensions, same score
anchors, same weights, same critical failures, same output JSON
schema. The only thing that changes is the opening paragraph that
describes what kind of Cosmos analysis Llama is evaluating. This
was a deliberate choice — it means the four scores can be placed
side by side in a table without any normalisation or calibration.
A score of 4.0 from eval_fault_detection.txt means the same thing
as a score of 4.0 from eval_process_quality.txt, because they were
graded on the same scale.


Why Llama, not Cosmos, does the evaluation

Cosmos is the model under test. Having it evaluate its own output
would be circular. Llama 3 was chosen because it runs locally via
Ollama, produces structured JSON output reliably, and is large
enough to follow a detailed rubric without losing track of the
criteria. The temperature is set to 0.1 to minimise scoring
variance between runs.


Structured JSON output

The eval prompts require JSON output and Ollama's format: "json"
flag is used to enforce it. This means every evaluation produces
machine-readable scores that can be aggregated, compared, or
plotted without manual parsing. The JSON includes per-criterion
scores with justification strings, so the reasoning behind each
score is preserved alongside the number.


No waypoint recommendations in eval prompts

Unlike the Cosmos prompts, the eval prompts do not ask for
recommended_waypoints. The evaluation stage is about scoring
what happened, not proposing what should happen next. Keeping
the eval output simple also reduces the chance of Llama producing
malformed JSON — the fewer fields it has to fill, the more
reliable the output.

The one exception is eval_screw.txt, which does not ask for
waypoints either, even though its Cosmos counterpart does. This
is intentional — the Cosmos-suggested waypoints are evaluated
implicitly through the Consistency criterion, not as a separate
scored field.


--- Output File Naming ---

Evaluation results are saved as:

    outputs/eval/eval_<slug>_<trace_id>_<timestamp>.json

Where <slug> is one of: screw, fault_detection, energy_dynamics,
process_quality. The trace_id links back to the original screw trace,
and the timestamp records when the evaluation was run. Each JSON
file also contains a _meta block with the Cosmos file path, eval
prompt name, Llama model name, and elapsed time, so the full
provenance chain is traceable from evaluation back to trace.
